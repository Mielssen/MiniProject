## ADR-0001. Поділ моноліту на сервіси

### Контекст
Один моноліт, п'ять контролерів, спільна БД:
* **Auth** (`credentials`, `user_details`) — читають усі;
* **Admin** — агрегує дані Auth + Tour + Booking для статистики;
* **Booking** (`bookings`, `booking_persons`) — залежить від Tour (ціна/дати) і Auth (дані користувача);
* **Tour** (`tours`, `tour_assets`) — напряму видаляє записи з `bookings` при видаленні туру;
* **SavedPerson** — ізольований.

### Варіанти
* **Auth + Tour + Booking** — три сервіси за бізнес-можливостями, кожна таблиця має одного власника.
* **Auth + один спільний Domain-сервіс** (Tour + Booking разом) — менше мережі, але легко знову зростається в моноліт.
* **Залишити моноліт, винести лише Auth** — мінімальні зміни, але не прибирає прямий доступ Tour -> Booking таблиць.

### Рішення
Обираємо варіант 1: Auth-сервіс (`users`), Tour-сервіс (`tours`), Booking-сервіс (`bookings`, `saved persons`) — поділ за володінням даними, один власник на таблицю.

### Наслідки
* Booking має питати Tour-сервіс за ціною/датами туру замість прямого JOIN — з'являється мережевий виклик і затримка.
* Дані користувача (ім'я, телефон) в Booking стають узгодженими, а не live-JOIN.
* Видалення туру більше не може напряму чистити чужі таблиці бронювань — потрібна подія (`TourDeleted`) замість прямого видалення.
* Втрачаємо єдину ACID-транзакцію на пов'язані зміни (тур + бронювання)

## ADR-0002. Спосіб маршрутизації зовнішніх запитів

### Контекст
Після поділу на три сервіси (ADR-0001) клієнту потрібна одна точка входу замість трьох адрес, плюс єдине місце для перевірки JWT і ролей.

### Варіанти
* **Без шлюзу** — клієнт сам звертається до кожного сервісу; просто, але перевірку токена й ролей довелось би дублювати в кожному сервісі.
* **Ocelot** — готовий API Gateway на .NET, маршрути й правила описуються декларативно в `ocelot.json`, без написання власного проксі-коду.
* **YARP** — гнучкіший, але потребує більше коду для налаштування.

### Рішення
Обираємо Ocelot: конфігурація маршрутів у JSON без написання власного коду, готова підтримка JWT-автентифікації через `AuthenticationOptions` у конфігу маршруту, легко описати три upstream-сервіси (Auth, Tour, Booking) окремими блоками `Routes`.

### Наслідки
* Клієнт працює з одним base URL; Ocelot перевіряє JWT і роль ще до того, як запит дійде до сервісу.
* З'являється додаткова мережева ланка й точка відмови — якщо Ocelot падає, падає весь доступ.
* Адмін-статистика (зараз один SQL-запит) вимагатиме або об'єднання кількох відповідей в одну, або окремого сервісу-агрегатора.
* Кожна зміна маршруту вимагає оновлення `ocelot.json` — потрібно стежити, щоб конфіг не розходився з реальними ендпоінтами сервісів.
