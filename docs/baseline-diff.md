# Порівняння поведінки до та після винесення BookingService

## Мета

Мета порівняння — перевірити поведінку API до та після винесення операцій бронювання з моноліту в окремий BookingService.

Для базового порівняння використовувалися збережені відповіді старої реалізації з Postman. Запити до нової реалізації виконувалися через API Gateway за адресою `http://localhost:5000`.

Стара реалізація перевірялася через `http://localhost:5272`. Результати збережені в колекції Postman `TravelManager Baseline`.

## Додаткові перевірки

- Перевірено маршрутизацію запитів через API Gateway.
- Інтеграційні тести BookingService виконуються успішно.
- Тайм-аут виклику CatalogService тривалістю 2 секунди перевірено вручну.
- Ідемпотентність створення бронювання перевірено вручну.
- Для перевірок нової реалізації використовувалася адреса API Gateway `http://localhost:5000`.
- Збережені базові та перевірочні запити містяться в `tests/baseline/TravelManager Baseline.postman_collection.json`.

## Висновок

Операції бронювання винесено з моноліту в окремий BookingService із власною базою даних `booking_service_db`. Взаємодія з AuthService виконується через HTTP, а з CatalogService — через gRPC із граничним часом очікування 2 секунди. Маршрутизацію через API Gateway та основні сценарії роботи перевірено.

За збереженими відповідями підтверджено збіг HTTP-статусів для перевірених сценаріїв автентифікації, доступу та зміни статусу бронювання. Для помилок неіснуючого бронювання й неіснуючого туру виявлено різницю в структурі JSON: стара реалізація містить поле `errors: null`, якого немає в новій відповіді. Списки бронювань містять різні записи, оскільки сервіси використовують окремі бази даних.

Отже, перевірені сценарії підтверджують збереження основної поведінки API, але повну ідентичність усіх відповідей не можна стверджувати через виявлені відмінності структури JSON і відсутність збереженого результату для окремих сценаріїв.
