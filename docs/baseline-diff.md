# Порівняння поведінки до та після винесення BookingService

## Мета

Мета порівняння — перевірити, чи збереглася поведінка API після винесення операцій бронювання з моноліту в окремий BookingService.

Базові запити виконувалися проти старої реалізації. Перевірки нової реалізації виконувалися через API Gateway за адресою `http://localhost:5000`.

## Результати перевірки

| Сценарій | Було — моноліт | Стало — BookingService | Чи є різниця |
|---|---|---|---|
| Отримання списку бронювань | HTTP 200, список бронювань | HTTP 200, список бронювань | Статус збігається. Повну структуру потрібно порівнювати за збереженими відповідями |
| Отримання списку без токена | Потрібно звірити з baseline-відповіддю | HTTP 401 | Потрібне точне порівняння |
| Отримання списку з роллю користувача | Потрібно звірити з baseline-відповіддю | HTTP 403 | Потрібне точне порівняння |
| Перегляд власних бронювань | Потрібно звірити з baseline-відповіддю | HTTP 200 | Потрібне порівняння структури JSON |
| Зміна статусу бронювання менеджером | Потрібно звірити з baseline-відповіддю | HTTP 200 | Потрібне порівняння тіла відповіді |
| Зміна статусу користувачем без відповідних прав | Потрібно звірити з baseline-відповіддю | HTTP 403 | Потрібне точне порівняння |
| Зміна статусу неіснуючого бронювання | Потрібно звірити з baseline-відповіддю | HTTP 400, код `NOT_FOUND` | Потрібно порівняти з поведінкою моноліту |
| Створення бронювання з невалідними даними | Потрібно звірити з baseline-відповіддю | HTTP 400, помилка валідації | Потрібно порівняти повідомлення та структуру JSON |
| Створення бронювання з неіснуючим туром | Потрібно звірити з baseline-відповіддю | HTTP 400, код `NOT_FOUND` | Потрібно порівняти код статусу та повідомлення |
| Повторне створення з тим самим `Idempotency-Key` | У старій реалізації потрібно перевірити фактичну поведінку | Повторний запит перевірений вручну | Потрібно зафіксувати результат і порівняти з вимогами |

## Додаткові перевірки

- Перевірено маршрутизацію запитів через API Gateway.
- Інтеграційні тести BookingService виконуються успішно.
- Тайм-аут виклику CatalogService на 2 секунди перевірено вручну.
- Ідемпотентність створення бронювання перевірено вручну.

## Висновок

BookingService винесено в окремий сервіс із власною базою даних. Взаємодія з AuthService та CatalogService виконується через міжсервісні виклики. Маршрутизацію через API Gateway та основні сценарії роботи перевірено.

Для остаточного підтвердження збереження поведінки потрібно зіставити точні статус-коди й тіла відповідей старого та нового API за збереженими результатами Postman. Незаповнені порівняння не вважаються підтвердженням повної еквівалентності.
